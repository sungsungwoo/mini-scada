# 📝 Mini SCADA 핵심 유스케이스 및 사용자 시나리오 (v1.0)

## 문서 목적

본 문서는 **Mini SCADA for Facility Monitoring**의 MVP 범위 내 핵심 사용자 흐름과 시스템 동작을 정의합니다.
특히 설비 모니터링 시스템의 핵심 리스크인 **Polling 실패, Online/Offline 상태 판단 오류, 알람 누락 또는 중복, 실시간 UI와 저장 데이터 간 불일치**가 실제 사용자 흐름 안에서 어떻게 동작하는지 명확히 설명하는 것을 목표로 합니다. 

---

## 시나리오 1. [관리자] 설비(Device) 등록 및 수집 대상 구성 (온보딩)

관리자가 신규 설비를 등록하고, Modbus 통신 정보와 센서(Tag) 메모리 맵을 설정하여 데이터 수집이 가능하도록 구성하는 과정입니다.

* **액터(Actor):** 관리자 (`ADMIN`)
* **사전 조건:** 관리자가 로그인한 상태이며, 신규 설비를 시스템에 연결하려는 상태
* **후행 결과:** 설비와 센서 정보가 저장되고, Polling 가능한 수집 대상이 생성됨

### 단계별 흐름 (Main Flow)

1. 관리자가 `[설비 등록]` 버튼을 클릭합니다.
2. 관리자가 설비 기본 정보를 입력합니다.
   * 설비명: `Boiler-01`
   * IP 주소: `192.168.0.10`
   * Port: `502`
   * Modbus Slave ID: `1`
   * Polling 주기: `2초`
3. 시스템은 입력값 형식을 검증합니다.
4. **관리자가 `[통신 테스트]` 버튼을 클릭하여, 입력한 네트워크 정보로 대상 설비와 1회 정상 응답이 이루어지는지 사전 검증합니다.**
5. 관리자가 수집 대상 센서(Tag)를 추가합니다.
   * Tag명: `temperature`
   * Register 주소: `40001`
   * Function Code: `Read Holding Registers`
   * 데이터 타입: `16-bit Integer`
6. 관리자가 추가 센서를 계속 등록합니다. (예: `pressure`, `rpm`, `humidity`)
7. 시스템은 `Device`와 `Tag` 설정을 저장합니다.
8. 시스템은 해당 설비를 Polling 스케줄 대상에 포함합니다.
9. 관리자는 설비 상세 화면에서 등록 결과를 확인합니다.

### 예외 흐름 (Alternate Flow)

* **잘못된 네트워크 설정 입력**
  * IP 주소 형식이 잘못되었거나 Port 범위를 벗어나면 저장을 차단합니다.
* **중복 설비 등록**
  * 동일한 IP 주소, Port, Slave ID 조합이 이미 존재하면 시스템은 중복 등록을 허용하지 않습니다.
* **잘못된 Register 매핑**
  * 주소 범위나 Function Code 조합이 유효하지 않으면 저장을 차단하거나 경고를 표시합니다.
* **통신 테스트 실패**
  * **방화벽, 네트워크 단절, 잘못된 Slave ID 등으로 통신 테스트가 실패할 경우, 명확한 에러 메시지를 표시하여 관리자가 설정을 재확인하도록 유도합니다.**

## 시나리오 2. [시스템] Modbus Polling을 통한 실시간 데이터 수집

시스템이 등록된 설비를 주기적으로 조회하여 센서 데이터를 수집하는 과정입니다.

* **액터(Actor):** 시스템
* **사전 조건:** 최소 1개 이상의 설비와 Tag가 등록되어 있으며 Polling이 활성화된 상태
* **후행 결과:** 최신 센서 값이 수집되어 저장되고, 후속 처리(상태 판단, 알람, 실시간 전파)의 입력값이 됨

### 단계별 흐름 (Main Flow)

1. `Spring Scheduler`가 설정된 주기에 따라 Polling 작업을 실행합니다.
2. 시스템은 Polling 대상 설비 목록을 조회합니다.
3. 시스템은 각 설비에 대해 비동기 요청을 전송합니다.
4. Modbus 응답을 수신합니다.
5. 시스템은 응답 데이터를 Tag 정의에 따라 파싱합니다.
6. 파싱된 값을 표준 형식으로 변환합니다.
7. 시스템은 수집 시각과 함께 시계열 데이터로 저장합니다.
8. 시스템은 해당 설비의 `last_seen` 값을 갱신합니다.

### 예외 흐름 (Alternate Flow)

* **Timeout 발생**
  * Modbus 응답이 설정된 타임아웃을 초과하면 해당 Polling은 실패 처리됩니다.
* **부분 응답 실패**
  * 일부 Tag만 읽기에 실패하면 성공한 Tag만 저장하고 실패 항목은 로그에 남깁니다.
* **데이터 변환 실패**
  * 잘못된 데이터 타입 매핑 등으로 파싱에 실패하면 해당 Tag 값을 폐기하고 에러 로그를 기록합니다.
* **Polling 중첩 지연 (Overlapping 및 Backpressure)**
  * **네트워크 지연으로 이전 주기 Polling 응답을 아직 대기 중인 상태에서 다음 Polling 주기가 도래할 경우, 해당 주기의 Polling을 건너뛰거나(Skip) 타임아웃을 엄격히 제한하여 스레드 풀 고갈 및 시스템 과부하를 방지합니다.**

## 시나리오 3. [운영자] 실시간 대시보드에서 설비 상태 모니터링

운영자가 대시보드에서 전체 설비 상태를 실시간으로 확인하는 과정입니다.

* **액터(Actor):** 운영자 (`OPERATOR`)
* **사전 조건:** 운영자가 로그인한 상태이며, 최소 1개 이상의 설비 데이터가 존재함
* **후행 결과:** 운영자가 최신 설비 상태, 센서 값, 알람 상태를 실시간으로 확인할 수 있음

### 단계별 흐름 (Main Flow)

1. 운영자가 대시보드 화면에 접속합니다.
2. 시스템은 초기 설비 목록과 최근 상태 데이터를 조회하여 화면에 렌더링합니다.
3. 운영자 화면은 MQTT over WebSockets 연결을 생성합니다.
4. 시스템은 신규 센서 값 또는 상태 변경 이벤트를 MQTT로 Publish합니다.
5. 운영자 화면은 실시간 메시지를 수신합니다.
6. 대시보드에는 다음 정보가 갱신됩니다.
   * 설비명
   * 실시간 센서 값
   * 네트워크 상태 (`Online` / `Offline`)
   * 알람 상태 (`Normal` / `Warning` / `Critical`)
   * 마지막 수신 시각 (`last_seen`)
7. 운영자는 전체 설비 상태를 하나의 화면에서 지속적으로 확인합니다.

### 예외 흐름 (Alternate Flow)

* **실시간 연결 실패**
  * MQTT WebSocket 연결이 끊어지면 클라이언트는 자동 재연결을 시도합니다.
* **실시간 메시지 수신 지연**
  * 최신 이벤트가 늦게 도착하면 화면은 마지막 저장값 기준으로 유지되며, 필요 시 stale 상태를 표시할 수 있습니다.

## 시나리오 4. [시스템] Online / Offline 상태 판단 및 상태 전파

시스템이 설비의 통신 상태를 평가하여 Online/Offline 여부를 판단하는 과정입니다.

* **액터(Actor):** 시스템
* **사전 조건:** 설비별로 `last_seen`이 기록되고 있으며 상태 판단 기준 시간이 설정되어 있음
* **후행 결과:** 설비 상태가 최신 기준으로 판정되고, UI와 알람 시스템에 반영됨

### 단계별 흐름 (Main Flow)

1. 시스템은 데이터 수집 성공 시 해당 설비의 `last_seen`을 갱신합니다.
2. 별도 상태 평가 로직이 주기적으로 현재 시간과 `last_seen`을 비교합니다.
3. 설정된 threshold 이내이면 설비를 `ONLINE`으로 판단합니다.
4. threshold를 초과하면 설비를 `OFFLINE`으로 판단합니다.
5. 상태가 이전 값과 달라졌다면 상태 변경 이벤트를 생성합니다.
6. 시스템은 상태 정보를 저장하거나 갱신합니다.
7. 시스템은 MQTT Topic(`/scada/{deviceId}/status`)으로 상태 변경 이벤트를 Publish합니다.
8. **운영자 대시보드는 해당 설비 상태를 즉시 반영합니다. 이때 Offline 전환 시 UI의 실시간 센서 값은 마지막 수집 값을 유지하되, 데이터가 갱신되지 않고 있음을 명확히 인지할 수 있도록 시각적으로 구분(예: 회색 음영 처리, Stale Data UI 적용)합니다.**

### 예외 흐름 (Alternate Flow)

* **일시적 지연**
  * 짧은 Polling 지연은 즉시 Offline으로 전환하지 않고 threshold 기준을 유지합니다.
* **연속 통신 실패**
  * 설정된 허용 범위를 넘는 연속 실패가 발생하면 설비를 Offline으로 전환합니다.
* **상태 흔들림(Flapping)**
  * Online/Offline 전환이 너무 자주 반복되는 경우, 완충 로직 또는 연속 성공/실패 횟수 기준을 둘 수 있습니다.

## 시나리오 5. [시스템] 임계값 초과 시 실시간 알람 생성

수집된 데이터가 Warning 또는 Critical 임계값을 초과했을 때 시스템이 알람을 생성하는 과정입니다.

* **액터(Actor):** 시스템
* **사전 조건:** 관리자에 의해 Tag별 임계값이 설정되어 있음
* **후행 결과:** 알람 이벤트가 생성되고 운영자에게 즉시 표시됨

### 단계별 흐름 (Main Flow)

1. 시스템이 신규 센서 값을 수집합니다.
2. 시스템은 해당 Tag의 임계값 정책을 조회합니다.
3. 수집값과 임계값을 비교합니다. **(비교 시 알람 데드밴드/Hysteresis 기준을 적용합니다.)**
4. 값이 정상 범위이면 `Normal` 상태를 유지합니다.
5. 값이 Warning 구간에 진입하면 `Warning` 알람을 생성합니다.
6. 값이 Critical 구간에 진입하면 `Critical` 알람을 생성합니다.
7. 상태 변화가 발생한 경우 알람 이력을 저장합니다.
8. 시스템은 MQTT Topic(`/scada/alarm`)으로 알람 이벤트를 Publish합니다.
9. 운영자 화면에는 Toast, 팝업, 배지 등으로 알람이 표시됩니다.

### 예외 흐름 (Alternate Flow)

* **알람 데드밴드(Deadband/Hysteresis) 적용**
  * **센서 값이 임계값 경계에서 미세하게 진동하여 발생하는 알람 폭주를 방지하기 위해, 복귀 임계값을 다르게 설정합니다. (예: Warning 발생은 70 이상이지만, Normal 상태 복귀는 65 이하로 떨어질 때만 인정)**
* **같은 상태의 반복 발생**
  * 동일 상태가 계속 유지되면 중복 알람을 무한 생성하지 않고 정책에 따라 억제할 수 있습니다.
* **수집 실패와 임계값 초과 동시 발생**
  * 센서 값이 없으면 임계값 비교 대신 통신 장애 알람을 우선 처리할 수 있습니다.

## 시나리오 6. [운영자] 알람 인지(Ack) 및 이력 확인

운영자가 발생한 알람을 확인하고 Ack 처리하는 과정입니다.

* **액터(Actor):** 운영자
* **사전 조건:** 미인지 상태의 알람이 존재함
* **후행 결과:** 알람이 확인된 상태로 변경되고, 운영 이력에 반영됨

### 단계별 흐름 (Main Flow)

1. 운영자가 알람 패널 또는 알람 목록 화면에 진입합니다.
2. 시스템은 최근 알람 이력을 조회합니다.
3. 운영자는 특정 알람을 선택합니다.
4. 운영자는 알람 상세 정보를 확인합니다. (설비명, Tag명, 발생 시각, 알람 레벨, 발생 값)
5. 운영자가 `[Ack]` 버튼을 클릭합니다.
6. 시스템은 해당 알람을 인지 처리합니다.
7. 알람 목록에서 상태가 `Acknowledged`로 변경됩니다.
8. **대시보드 상의 점멸 효과나 경고음 등 시각적/청각적 알림은 중단됩니다. 단, 실제 센서 값이 정상 범위(Normal)로 복귀하기 전까지 해당 설비의 상태 아이콘이나 태그 패널은 여전히 Warning/Critical 색상을 유지하여 현 상태를 정확히 고지합니다.**
9. 운영자는 이후에도 이력 화면에서 해당 알람을 다시 조회할 수 있습니다.

### 예외 흐름 (Alternate Flow)

* **이미 Ack 처리된 알람**
  * 이미 인지된 알람은 중복 Ack를 허용하지 않거나, 재처리 없이 현재 상태만 반환합니다.
* **실시간 반영 실패**
  * 화면 반영이 지연되더라도 재조회 시 최종 Ack 상태를 확인할 수 있습니다.

## 시나리오 7. [운영자] 설비 상세 화면에서 시계열 데이터와 장애 이력 확인

운영자가 단일 설비를 선택하여 시간 흐름에 따른 상태를 분석하는 과정입니다.

* **액터(Actor):** 운영자
* **사전 조건:** 대상 설비에 대해 시계열 데이터가 저장되어 있음
* **후행 결과:** 운영자가 현재 상태뿐 아니라 최근 추세와 장애 이력을 함께 분석할 수 있음

### 단계별 흐름 (Main Flow)

1. 운영자가 대시보드에서 특정 설비를 선택합니다.
2. 시스템은 설비 상세 화면으로 이동합니다.
3. 시스템은 최근 N시간 시계열 데이터를 조회합니다. **(TimescaleDB의 Continuous Aggregates 등을 활용하여 장기 데이터 조회 성능을 최적화합니다.)**
4. 시스템은 실시간 게이지와 라인 차트를 렌더링합니다.
5. 시스템은 최근 알람 및 장애 이력을 함께 표시합니다.
6. 운영자는 현재 값과 추세를 비교합니다.
7. 운영자는 이상 징후가 단발성인지 지속성인지 판단합니다.

### 예외 흐름 (Alternate Flow)

* **조회 구간 데이터 부족**
  * 해당 기간 데이터가 적거나 없으면 빈 상태 메시지를 표시합니다.
* **집계 데이터 사용**
  * 장기간 조회에서는 원본 대신 Downsampling 데이터로 차트를 렌더링할 수 있습니다.

## 시나리오 8. [관리자] 임계값 및 데이터 보존 정책 변경

관리자가 설비 운영 기준에 맞게 알람 임계값과 데이터 보존 정책을 조정하는 과정입니다.

* **액터(Actor):** 관리자
* **사전 조건:** 설비와 Tag가 이미 등록되어 있음
* **후행 결과:** 이후 수집 데이터에 대해 새로운 기준이 적용됨

### 단계별 흐름 (Main Flow)

1. 관리자가 관리자 설정 화면에 진입합니다.
2. 특정 설비 또는 Tag를 선택합니다.
3. 관리자가 임계값을 수정합니다.
   * Warning: `70`
   * Critical: `90`
   * **Deadband 설정 (선택 사항)**
4. 관리자가 데이터 정책을 수정합니다.
   * 원본 데이터 보존 기간
   * Downsampling 주기
5. 시스템은 입력값을 검증합니다.
6. 시스템은 설정 변경 내용을 저장합니다.
7. 이후 수집되는 데이터부터 변경된 정책을 적용합니다.

### 예외 흐름 (Alternate Flow)

* **비정상 임계값 입력**
  * Warning 값이 Critical보다 크거나 같은 경우 저장을 차단합니다.
* **보존 정책 충돌**
  * 원본 보존 기간보다 Downsampling 정책이 모순되면 저장을 차단하거나 수정 가이드를 표시합니다.

## 시나리오 9. [시스템 공통] 실시간 전파 실패 시 상태 복구

MQTT 실시간 전파가 실패하더라도, 사용자가 재조회 시 최종 상태를 정확히 확인할 수 있도록 복구하는 과정입니다.

* **액터(Actor):** 시스템, 운영자, 관리자
* **사전 조건:** 데이터는 TSDB 또는 시스템 저장소에 정상 반영되었으나, MQTT 전달 또는 UI 수신이 실패한 상태
* **후행 결과:** 사용자가 새로고침 또는 재진입 시 최신 상태를 확인할 수 있음

### 단계별 흐름 (Main Flow)

1. 시스템은 수집 데이터와 상태 변경 결과를 먼저 저장합니다.
2. 저장 이후 MQTT Publish를 시도합니다.
3. 네트워크 문제 등으로 일부 클라이언트가 이벤트를 놓칠 수 있습니다.
4. 사용자가 대시보드 또는 상세 화면을 새로고침하거나 재진입합니다. **(웹소켓 재연결 시 시스템은 최신 상태 동기화를 위해 REST API를 1회 호출하여 화면 데이터를 초기화합니다.)**
5. 시스템은 저장소의 최신 데이터를 다시 조회합니다.
6. 화면은 재조회 결과를 기준으로 최종 상태를 렌더링합니다.
7. 사용자는 실시간 이벤트를 놓쳤더라도 최신 상태를 정확히 확인할 수 있습니다.

### 예외 흐름 (Alternate Flow)

* **MQTT 재연결 실패 지속**
  * 클라이언트는 주기적으로 재연결을 시도하고, 실패 시에도 마지막 정상 조회 데이터를 유지합니다.
* **저장 실패**
  * DB 저장에 실패한 경우에는 실시간 이벤트를 보내지 않거나, 전송하더라도 최종 상태로 간주하지 않습니다.

## 공통 비즈니스 규칙 요약

1. **최종 상태의 기준은 저장소(DB/TSDB)이다.**
   * MQTT는 실시간 전달 채널이며, 최종 진실 공급원(Source of Truth)은 저장된 데이터이다. 
2. **Polling 성공 시에만 `last_seen`을 갱신한다.**
   * 설비 Online/Offline 판정은 마지막 정상 수집 시각을 기준으로 한다. 
3. **알람은 상태 변화 중심으로 관리하며, 데드밴드(Deadband)를 적용한다.**
   * 동일 상태가 반복될 때는 중복 알람 폭주를 방지하고, 미세한 진동(Flapping)으로 인한 잦은 알람 발생을 제어한다.
4. **실시간 반영 실패는 재조회로 복구 가능해야 한다.**
   * UI는 MQTT 이벤트를 놓치더라도 API 또는 저장소 재조회로 최종 상태를 복구할 수 있어야 한다.
5. **관리자 설정은 이후 수집 로직에 직접 영향을 준다.**
   * Polling 주기, Register 맵, 임계값, 보존 정책은 모두 시스템 동작 기준값이다. 
6. **운영자와 관리자의 역할은 분리된다.**
   * 운영자는 모니터링 및 알람 대응을 수행하고,
   * 관리자는 설비/Tag/정책 설정을 수행한다.
